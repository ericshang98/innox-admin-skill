# 直接为用户生成验收单

触发：“帮我做／填验收单”“这几张发票整理成验收单”“验收单补照片”等。目标是交付按学院模板填写的 Word 草稿、附件和缺件说明；不是只推荐模板或教用户自己排版。原件、字段和适用性见 [模板说明](templates.md)。

## 只问本次需要的事实

先读团队／成员档案，识别正在办理的 case。只做验收单时不要求用户重新讲完整采购历史。由已有材料确定采购途径及实物／服务；两者不明且影响选表时，才追问。自采服务、混合项目表格适用性不清时先整理明细和交付材料，标明待学院确认，不把模板猜成已经适用。

1. **提取明细**：从订单、合同、发票读取名称、规格、数量、单价、金额和币种；多张票据保留来源对应，不把重复的同张票算两次。订单数量不等于送达数量，实际收货不明时补问。
2. **核对金额**：按真实数量和单价计算小计，再核对发票、付款和合同。折扣、运费、税额、部分交付、外币等差异先解释；不能修改真实单价凑平。已有明确数据不重复询问。
3. **收集交付证据**：货物使用用户实际收货照片，可补简短说明；服务使用真实交付物、服务期间和合同要求。不得生成假的验收照片或把订单截图直接当实物照片。图片文件只处理用户提供的证据。
4. **生成草稿**：清除模板样例，填事实字段，插入照片；服务表保留第二张履约评价表。缺少照片或签字可先输出草稿和准确缺件说明。没有发生验收时日期留空，不填“已验收”。
5. **交付**：给用户可编辑 `.docx`、按需生成的预览 PDF，以及简短说明：“已填哪些内容、还缺什么、谁需要签哪些位置”。输出链接指向真实生成的文件；没有成功生成时不能声称已完成。

验收结论、通过／不通过勾选、评分、签名及公章由有权人员据实完成。脚本会清除自采原表自带的勾选符号，将合格／不合格恢复为未选方框，不自动勾合格，不打满分。对“交付事实”和“验收判断”分别记录。

## 生成工具

使用 `scripts/fill_acceptance.py`，需要 Python 3.10+、`python-docx` 和 `Pillow`；依赖范围见 `scripts/requirements.txt`。优先使用运行环境已有文档工具环境。用户不需要安装或操作脚本，Agent 负责执行；环境无文件工具时如实说明不能在此生成 Word，并交付已整理内容，不冒充文件。

Agent 把提取并核对的事实写入本次私有目录的 JSON，再执行：

```bash
python3 scripts/fill_acceptance.py --input /private/case/acceptance.json --output /private/case/验收单草稿-v1.docx
```

脚本验证模板哈希、清除示例、扩展明细行、核对计算、插入 PNG／JPEG 照片，输出 Word 与 `.materials.json` 材料记录。记录内含缺项、原模板哈希、金额及附件来源；Agent 把缺件翻译成易懂的话，不让用户看 JSON。原始模板只读；已有输出不会覆盖，修改时使用新版本文件名。填好的文件不得提交 GitHub。

## 货物／自采输入

以下是数据结构示例，不是用户真实交易。金额和数量使用十进制字符串；`items.quantity` 为实际送达数量。图片路径相对于输入 JSON 的目录，也可为绝对路径。

```json
{
  "template": "self-purchase",
  "currency": "CNY",
  "items": [
    {"name": "实际品名", "model": "实际型号", "quantity": "2", "unit_price": "25.00", "subtotal": "50.00", "note": "对应发票及明细行"}
  ],
  "invoice_total": "50.00",
  "photos": [{"path": "收货照片.jpg", "caption": "实际照片对应的物品说明"}],
  "acceptance_date": null,
  "attachments": [{"path": "原始发票.pdf", "purpose": "明细金额依据"}],
  "missing": []
}
```

`template` 为 `self-purchase` 或 `goods`。`subtotal`、`invoice_total` 有据才传；缺发票合计时脚本会提醒核对。没有照片传空数组；不知道验收日期留空。当前脚本只处理人民币，外币需依据已确认口径准备人民币明细及折算说明后再使用，不把原币数字直接当人民币填入。

## 服务输入

```json
{
  "template": "service",
  "currency": "CNY",
  "service": {
    "project": "真实项目名称",
    "handler": "真实采购经办人",
    "department": "真实采购经办部门",
    "request_department": "真实需求部门",
    "supplier": "供应商合同主体",
    "period": "真实服务起止日期",
    "content": "真实服务内容与交付物",
    "contract_total": "3000.00",
    "checks": [{"criterion": "合同中约定的验收项目", "evidence": "已提供的交付证据说明；不写未经确认的通过结论"}]
  },
  "attachments": [],
  "missing": []
}
```

服务字段未知时可省略或留空，脚本清除样例后列为缺项。`contract_total` 是完整合同价，不是此次付款额。`checks` 必须依据本次合同／交付整理，不能沿用原表活动搭建的样例分项；通过／不通过留给真人判断。评分项保留原表，适用性需学院核对，不适用时不自行改权重。

## 文件检查与续办

生成后打开／渲染 Word，检查所有页面：中文字体、明细行、金额、照片比例、合并单元格、分页和签署区。当前原始服务表含尾部空白页，脚本仅在副本中清除尾部空章节；其他章节与原始文件不改。字体缺失导致方框时，可在输入增加 `render_font`，指定运行环境已存在的中文字体后重新渲染，并记录这一版式调整；不要静默改变未出现问题的字体。

如果字体在系统中存在但渲染仍出现方框，先检查渲染器能否读取该字体目录；可使用任务私有的字体配置修复预览，不修改系统字体或用户应用配置。不能把预览缺字当成文档内容缺失，更不能在未检查的情况下声称版式正常。

对数量很多、照片很多或长服务说明，逐页检查增页后表头与签署区。不能因为脚本退出成功就称版式已验收。若不能渲染，交付为“待版式检查的草稿”。

把生成文件、输入事实、模板版本、材料记录和签署状态写回原 case。用户之后补照片、修金额或补签字时，沿用该 case 和新事实输出新版本，不重复询问团队信息，不覆盖已签署原件。签署后是否还需学院审批，按事项的真实状态继续处理。
